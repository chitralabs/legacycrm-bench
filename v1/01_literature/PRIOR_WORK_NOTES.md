# Prior Work Notes — LegacyCRM-Bench

Audit date: 2026-09-01. All works below were verified against primary sources (see REFERENCE_VERIFICATION.csv for URLs and verification methods). Notes are original prose based on the verified abstracts/records and publicly documented artifact pages.

**Critical positioning fact:** CRMArena (NAACL 2025) and CRMArena-Pro (2025) are existing, well-known CRM benchmarks from Salesforce AI Research. LegacyCRM-Bench must NOT claim to be the first CRM benchmark, the first Salesforce-schema benchmark, or the first enterprise-agent benchmark. Its defensible novelty is narrower: evaluating whether LLM-assisted *migration/modernization* of legacy CRM *customizations* (schema mappings, validation rules, workflow automations, RBAC/sharing rules, integrations, audit logging) preserves behavior — a migration-correctness benchmark, not a task-completion benchmark.

---

## 1. CRMArena (Huang et al., NAACL 2025; arXiv:2411.02305)

CRMArena evaluates whether LLM agents can perform professional CRM operational tasks inside a realistic, sandboxed Salesforce organization. The dataset is synthetic but deliberately realistic: sixteen interconnected industrial objects (accounts, orders, cases, knowledge articles, etc.) generated with latent variables such as complaint habits and policy violations, validated by CRM practitioners. Tasks span nine customer-service scenarios across three personas (service agent, analyst, manager), and the execution environment is a live Salesforce sandbox that agents query via ReAct-style prompting or function calling. The primary metric is task-completion accuracy against ground-truth answers; the paper reports that state-of-the-art agents complete under 58% of tasks with ReAct and under 65% with function calling. Evaluated models included leading proprietary and open LLMs of late 2024. Code and data are released publicly by Salesforce AI Research. Its limitation relative to LegacyCRM-Bench: it tests *operating* a CRM (answering questions, routing cases), not *migrating or re-implementing* CRM customizations, and it does not measure preservation of validation rules, RBAC semantics, or audit behavior under transformation. **This work already covers CRM** — it is the single closest naming/positioning risk.

## 2. CRMArena-Pro (Huang et al., 2025; arXiv:2505.18878)

CRMArena-Pro extends CRMArena from customer service to a holistic set of business scenarios — sales, service, and configure-price-quote (CPQ) style workflows — across both B2B and B2C settings, and adds multi-turn user interactions and confidentiality-awareness probes. Provenance is again synthetic-but-expert-validated data inside a Salesforce-style environment; the benchmark stresses realistic schemas and nineteen expert-validated tasks. Metrics are task completion plus dedicated measurement of confidentiality-aware behavior; reported results show even top agents around ~58% single-turn success, degrading sharply (~35%) in multi-turn settings. It evaluates a broad slate of frontier models. Artifacts are public. Relative to LegacyCRM-Bench, it still measures agent task execution against a *fixed, already-configured* CRM org; it does not create legacy-vs-target org pairs, does not test code/metadata transformation, and has no functional-equivalence or migration-fidelity metric. **This work also already covers CRM**, including access-restriction sensitivity — so LegacyCRM-Bench's RBAC angle must be framed as *preservation under migration*, not as introducing access-control awareness to CRM evaluation.

## 3. EnterpriseBench (Vishwakarma et al., EMNLP 2025; arXiv:2510.27287)

EnterpriseBench, from a Fujitsu research team, is a sandbox simulating an entire enterprise environment with 500 tasks spanning software engineering, HR, finance, and administrative domains. Its distinguishing design choices are simulated data-source fragmentation, access-control hierarchies, and cross-functional workflows — agents must respect permissions while completing tasks. Tasks are generated from enterprise data sources with human curation; the environment is a closed sandbox rather than a live SaaS instance. The headline metric is task completion (best agents reach only ~41.8%). Artifact availability should be checked at camera-ready (EMNLP 2025 main). It differs from LegacyCRM-Bench in the same fundamental way as the CRMArena line: it benchmarks agents *doing work inside* an enterprise system, not *transforming* one enterprise system into another while preserving customization semantics. Its access-control-hierarchy modeling, however, overlaps with the RBAC dimension of LegacyCRM-Bench and must be cited.

## 4. tau-bench (Yao et al., 2024; arXiv:2406.12045)

tau-bench evaluates tool-using agents in realistic customer-facing domains (retail and airline) where the agent must interact with a simulated human user (LLM-simulated) and domain APIs while following domain policy documents. Task data is hand-constructed with databases and policies per domain; execution is via a lightweight open-source harness that compares the final database state against an annotated goal state — an objective, state-based success criterion. Its pass^k metric explicitly measures *reliability over repeated i.i.d. trials*, showing e.g. GPT-4o falls below 25% pass^8, which is directly relevant methodology for LegacyCRM-Bench's reproducibility/reliability claims. Models evaluated were frontier function-calling LLMs of mid-2024. Artifacts are fully public and widely reused (Sierra AI). It contains no CRM schema, no migration task, and no code transformation — but its database-state-diff evaluation and pass^k should be acknowledged as the methodological ancestors of any state-equivalence and repeated-trial metrics in LegacyCRM-Bench.

## 5. WorkBench (Styles et al., 2024; arXiv:2405.00823)

WorkBench places agents in a simulated workplace with five databases (email, calendar, analytics, CRM-like customer relationship data, project management), 26 tools, and 690 tasks. Provenance is synthetic sandbox data; evaluation is outcome-centric: a task counts as solved only if the resulting database state exactly matches the unique ground-truth state, which cleanly handles multiple valid action paths and side effects. Best 2024-era agents solved well under half of tasks, and the paper highlights consequential errors (e.g., emailing the wrong person). Artifacts are public. Notably, **WorkBench includes customer-relationship-management style data among its domains**, another reason LegacyCRM-Bench cannot claim CRM novelty per se. It does not address migration, legacy code, metadata transformation, or equivalence of business rules across platforms; its relevance is chiefly the predictable-outcome evaluation design.

## 6. WorkArena (Drouin et al., 2024; arXiv:2403.07718)

WorkArena benchmarks *web* agents on a live instance of ServiceNow — an actual enterprise SaaS platform adjacent to CRM — across ~29 task types (later expanded in WorkArena++) drawn from common knowledge-worker interactions: form filling, list filtering, knowledge retrieval. Provenance is the real ServiceNow developer instance UI with programmatically generated task instances and automatic validity checks; the harness (BrowserGym) is open source. Metrics are per-task success from environment-verified oracles. The paper found a significant gap between humans and agents. Because ServiceNow is a legitimate enterprise workflow/ITSM platform with heavy customization capability, WorkArena demonstrates that live-SaaS-platform benchmarks already exist; LegacyCRM-Bench's distinction is that its object of evaluation is the *customization artifacts themselves* (rules, workflows, RBAC) under migration, not UI task execution. No migration or equivalence testing appears in WorkArena.

## 7. SWE-bench (Jimenez et al., ICLR 2024; arXiv:2310.06770)

SWE-bench evaluates whether LMs can resolve real GitHub issues in twelve popular Python repositories; provenance is fully organic (2,294 real issue–pull-request pairs), and evaluation executes the repository's own test suite (fail-to-pass plus pass-to-pass tests) in containerized environments. Metrics are resolved-rate percentages; early models solved under 2%, and the benchmark became the de facto standard for repository-level coding agents, spawning Verified/Multimodal/Live variants. Artifacts are fully public and heavily maintained. Its relevance to LegacyCRM-Bench is as the template for execution-based, repository-scale, test-oracle evaluation — and as a cautionary tale, since later audits found solution leakage and weak-test issues, motivating LegacyCRM-Bench's contamination controls and test-adequacy arguments. It contains no CRM content and no cross-platform migration tasks; its tasks are within-repo bug fixes, not semantics-preserving re-implementation.

## 8. Lost in Translation (Pan et al., ICSE 2024; DOI 10.1145/3597503.3639226)

This is the key empirical study of LLM code-*translation* failure modes: the authors translated code across C, C++, Go, Java, and Python using general LLMs and specialized translation models on 1,700 code samples (including real-world projects), executing tests to check correctness. They found unsuccessful translation rates from 76.4% to 97.9% for real-world code and built a taxonomy of 15 bug categories covering syntactic and semantic errors, plus a mitigation prompt-engineering approach. Data and a reproducible harness are public. The study establishes that translation *correctness* — precisely the quantity LegacyCRM-Bench measures for CRM customizations — is a recognized open problem; but its subjects are general-purpose languages, not CRM DSLs (validation formulas, workflow metadata, Apex-like triggers), and it has no notion of RBAC, audit, or integration semantics. LegacyCRM-Bench should adopt/extend its bug taxonomy for migration defects.

## 9. CodeTransOcean (Yan et al., 2023; arXiv:2310.04951) and TransCoder (Lachaux et al., 2020; arXiv:2006.03511)

TransCoder introduced unsupervised neural translation among C++/Java/Python and, importantly, released 852 parallel functions with unit tests — the first widely used execution-checked translation testbed — reporting computational-accuracy rather than BLEU. CodeTransOcean broadened translation evaluation to multilingual and *niche/low-resource* pairs, including a LLMTrans dataset with executable evaluation and, notably, modernization-flavored directions involving legacy languages; it proposes Debugging Success Rate@K as an execution-based metric. Both are public. Together they define the lineage of execution-based translation metrics that LegacyCRM-Bench inherits. Neither handles multi-artifact enterprise customizations, declarative business rules, or platform metadata; both operate at function/program granularity, whereas CRM migration correctness is a property of an interacting configuration (schema + rules + workflows + permissions).

## 10. AlphaTrans (Ibrahimzada et al., FSE 2025; DOI 10.1145/3729379)

AlphaTrans is the strongest recent repository-level translation-and-*validation* system: a neuro-symbolic pipeline that decomposes whole projects, translates fragments Java-to-Python, and validates each fragment with GraalVM-based cross-language differential execution plus translated existing tests. Evaluated on ten real open-source projects (~6,899 source methods), it achieved high syntactic validity with a measured fraction of runtime-equivalent fragments, and it quantifies validation effort. Artifacts are public. This is the closest *methodological* prior for LegacyCRM-Bench's functional-equivalence checking (fragment-level differential testing during migration). The differences: AlphaTrans is a *technique* evaluated on generic Java projects, not a community benchmark; and it does not cover declarative platform customizations, RBAC, audit logging, or integration endpoints. LegacyCRM-Bench should position itself as providing the standardized benchmark such techniques currently lack in the enterprise-platform domain.

## 11. Python library migration line: PyMigBench (Islam et al., MSR 2023) and the ASE 2025 LLM study (Islam et al.)

PyMigBench curates 2,335 real migration-related code changes from open-source Python projects that swapped analogous libraries, giving organic provenance for *API/library migration* — a form of migration narrower than platform modernization. The follow-up ASE 2025 empirical study evaluates LLMs performing those migrations and measures how well generated changes match real developer changes and pass checks. Both artifacts are public. These works establish that "LLM-assisted migration" already has benchmarks at the library-API level; LegacyCRM-Bench differs in migrating *configured platform behavior* (multi-artifact, declarative + procedural, permission-laden) rather than call-site rewrites, but the paper must cite this line to scope its "migration benchmark" claim honestly.

## 12. IBM COBOL-to-Java validation line (Hans et al., arXiv:2504.10548; Kumar et al., arXiv:2506.10999; Froimovich et al., arXiv:2507.23356)

These 2025 industrial papers around IBM watsonx Code Assistant for Z address exactly the *verification* half of legacy modernization: automatically generating tests against original COBOL programs, validating equivalence of translated Java, and combining analytic checkers with LLM-as-judge quality scoring. Provenance is enterprise COBOL code (partially proprietary); execution environments are mainframe/JVM test harnesses; metrics are equivalence-test pass rates and quality scores. Artifact availability is limited (industrial settings), which weakens reproducibility — a gap LegacyCRM-Bench can explicitly target with a fully open, reproducible harness. These works prove that legacy-modernization equivalence testing is an active area; LegacyCRM-Bench's differentiation is domain (CRM customizations, not COBOL batch programs), breadth of preserved properties (RBAC, audit, integrations — not just I/O behavior), and open benchmark packaging.

### Adjacent verified works informing methodology (brief)

- **EvalPlus (Liu et al., 2023)**: showed HumanEval's tests were too weak — pass@1 dropped up to ~28.9 points with 80x more tests; motivates test-adequacy arguments for any equivalence oracle in LegacyCRM-Bench.
- **Csmith (Yang et al., PLDI 2011)**: canonical differential-testing precedent (randomized programs, cross-implementation output comparison) underpinning the migration-equivalence oracle design.
- **Pearce et al. (IEEE S&P 2022) / CyberSecEval 1–2 (Meta)**: security evaluation of generated code; relevant because migrated CRM code (triggers, integration handlers) can introduce vulnerabilities and permission bypasses.
- **Fisler et al. (ICSE 2005, Margrave)**: access-control policy verification and *change-impact analysis* — the classical foundation for checking that RBAC semantics survive a migration.
- **Contamination line (Golchin & Surdeanu; Sainz et al.; LiveCodeBench)**: motivates synthetic-org generation and time-stamped task release in LegacyCRM-Bench.
- **Reliability/statistics line (tau-bench pass^k; AgentBoard; Zhu et al. 2025 rigorous-agentic-benchmarks; Miller 2024 error bars; Efron 1979; Dror et al. 2018)**: motivates repeated-trial metrics, CIs via bootstrap, and significance testing in the eval protocol.
